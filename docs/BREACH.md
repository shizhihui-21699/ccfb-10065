# 泄露库与 k-匿名查询

## 1. 协议

```
客户端                                          服务端
  |                                               |
  |  h = SHA1(password)                           |
  |  prefix = h[0..4]   （4 位十六进制 = 16 bit） |
  | -------- GET /range/5baa --------------------> |
  |                                               | 读该前缀的桶
  | <------- 35 位后缀:次数（每行一条）----------- |
  |                                               |
  | 本地比对完整后缀 → 命中次数                    |
```

服务端从头到尾**只见到 4 位十六进制前缀**。它不知道完整哈希，
更不知道口令。客户端在本地比对后缀，命中的事实只留在浏览器里。

## 2. k 取多少：为什么不用 HIBP 的 20 bit

k-匿名的 k 是「单次查询落到的桶里有多少条记录」。k 太小，攻击者
（或好奇的服务端）可以用桶里的后缀去撞库反推查询者查了什么。

实测本语料（245 万条 ≥2 次的唯一口令）：

| 前缀位宽 | 桶数 | k 最小 | k 中位 | k p90 | 单桶响应 |
|---|---|---|---|---|---|
| 20 bit（HIBP 的选择） | 947 976 | **1** | **2** | 4 | < 100 B |
| 16 bit（本项目） | 65 536 | **12** | **37** | 45 | ~1.5 KB |
| 12 bit | 4 096 | 510 | 601 | 632 | ~25 KB |

HIBP 能用 20 bit 是因为它有**6 亿条**口令，每个前缀下仍有数十条记录。
本项目的语料小两个数量级，20 bit 下 k 中位数只有 2——匿名性不足。

**16 bit** 是这份数据下的平衡点：k ≥ 12（满足常见的 k≥10 要求），
单桶响应 1.5 KB 可接受。代价是前缀从 65 万分之一降到 6.5 万分之一
的口令空间；但服务端仍然看不到完整哈希与口令，这一层保护不变，
泄露的只是「这个桶里还有哪些后缀」——而桶内容本来就是服务端持有的
公开泄露数据。

## 3. 存储布局

**不做「一前缀一文件」。** 最初按 `bucket_5b/5baa6.txt` 布局，实测
95 万个小文件占用 **3.6 GB**（文件系统块 4 KB 起，每个文件 40 字节
内容也要占一整个块）。改为拼接单文件 + 偏移索引：

```
breach.bin   所有桶按前缀值升序首尾相接，每条 "<36位后缀>:<次数>\n"
breach.idx   "PMB1" + u32 桶数 + u32 前缀位宽 + 每桶 (u64 offset, u32 len)
```

- `breach.bin` 92 MB，`breach.idx` 768 KB；
- 查询是一次 `Vec` 切片（服务端启动时把两个文件读进内存），
  实测响应 9 µs。

## 4. 生成

```bash
python3 tools/build_breach_db.py \
    --raw data/raw/rockyou-withcount.txt \
    --prefix-bits 16 --min-count 2
```

输出会打印 k 的分布。脚本里有硬性检查：**最小 k < 10 时打印警告**，
提示减小 `--prefix-bits` 或放宽 `--min-count`。

收录标准是「出现 ≥2 次」。只出现 1 次的口令有 1190 万条，
收录它们会把 k 稀释到 1，且这些口令本身就近似随机串，没有防护价值。

## 5. 服务的接口

| 路径 | 说明 |
|---|---|
| `GET /range/{prefix}` | 前缀查询，`prefix` 为 4 位小写十六进制 |
| `GET /healthz` | JSON 健康检查（含请求数、命中数、平均耗时） |
| `GET /metrics` | Prometheus 文本格式 |
| `GET /`、`/index.html`、`/passmeter.js`、`/passmeter_wasm.wasm`、`/dict2.bin` | 静态站点 |

`/range` 的响应带 `Cache-Control: public, max-age=300`（桶内容基本不变），
`/healthz`、`/metrics` 带 `no-store`。静态资源做了路径穿越防护
（拒绝 `..`、绝对路径、反斜杠）。

## 6. 隐私边界（说清楚哪里没做到）

**做到了**：
- 查询请求只含 16 bit 前缀；
- 服务端不落地任何请求日志（只累加计数）；
- 完整 SHA-1 在浏览器内计算（WASM 的 `sha1Hex`），从不发送。

**没做到**：
- 16 bit 前缀仍是一个可关联的查询标识。同一个前缀反复查询会被
  服务端的计数器观察到（虽然不记录来源 IP，但网络层可以看到）。
  要更强的话需要加盲签名或私有信息检索（PIR），超出本项目范围；
- 传输层未强制 TLS。生产部署必须放在 HTTPS 之后，否则前缀仍是明文；
- 泄露库只有 rockyou 一个来源，覆盖不到近十年的新泄露。

## 7. 为什么 SHA-1 是可以的

SHA-1 的碰撞攻击不适用于这里：我们不需要抗碰撞，只需要
「给定口令难以反推、且不同口令的前缀分布均匀」。SHA-1 在这两点上
仍然合格，且几乎所有泄露库工具（HIBP、hashcat 的 `--show`）都用它，
互通性更好。

如果将来要换算法，只需改 `passmeter-core/src/hash.rs` 的 `sha1()` 与
`breach.rs` 的 `PREFIX_HEX_LEN`，并重建泄露库——协议本身不变。
